## TL;DR · 最小可用 5 条

> 如果项目很小、只能记 5 条，先做到这 5 条——它们能消灭大部分文档矛盾；其余条款按项目复杂度逐步加。

1. **一份事实源**：所有数字只在一处维护，其他文档引用。
2. **一个入口**：新人和 AI 先读入口文件，再读事实源与契约。
3. **一条变更日志**：倒序、同日合并、写验证、记发布三元组。
4. **一次定期审计**：双周一次，结论必须回读源码/实测。
5. **一条防漂移规则**：同源双份必须互相点名并同时修改。

## 0. 设计目标与总原则

### 0.1 要解决的六个问题

| 目标 | 反面症状 | 对应机制 |
|---|---|---|
| **协调性** | 同一事实在不同文档里数值不同、互相矛盾 | 单一真相源（§2.1） |
| **有效性** | 文档说的和代码/线上实际不符 | 契约绑定 + 自动巡检（§2.5、§5） |
| **及时性** | 改完代码不更新文档，文档永远落后 | 变更闭环 + 发布日期（§4） |
| **系统性** | 文档散落、职责重叠、找不到入口 | 分层与入口（§1） |
| **完整性** | 关键决策/环境配置/回滚方式没记录 | 必答清单模板（§8） |
| **谱系性** | 规范复制到多项目后各自改编、互相失联；两个副本相见时不知对方进化了什么，改进丢失或被重复吸收 | 谱系块 + 进化登记 + 合并协议（§12.3） |

### 0.2 一条总原则

> **单一真相源（SSOT）＋ 单一入口 ＋ 变更留痕 ＋ 定期审计。**

任何与此冲突的做法（比如「把同一个数字复制到多份文档方便阅读」）都应被本规范否定。

### 0.3 目标—规则覆盖矩阵

> 用法：**新增或修改规则时，必须在本表登记它服务哪个目标**——否则规则会越堆越多，却没人知道它防的到底是什么。

| 目标 | 主要规则（§2） | 配套机制 | 自查问题 |
|---|---|---|---|
| **协调性** | 2.1 单一真相源、2.7 双份产物防御 | 1.3 事实 ID、3.5 命名统一、§5 审计 | 同一事实是否只在一处维护？同源副本是否互相点名？ |
| **有效性** | 2.5 契约绑定、2.6 发布三重记账、2.8 环境专属配置 | 5.1 自动巡检、5.6 健康度量、3.2 可验证、11.1 证据要求 | 文档说的能否用命令/实测复现？ |
| **及时性** | 2.3 变更留痕、2.4 只留日期、§4 变更闭环 | 4.2 变更影响矩阵、5.4 新鲜度 SLO、5.2 定期审计 | 这次改动是否已回填日志/事实源/契约？ |
| **系统性** | §1 分层、2.2 单一入口 | 1.4 目录与命名、1.5 新增准入、§6 生命周期、6.1 ADR、§8 模板 | 每份文档只答一类问题吗？新人有单一入口吗？ |
| **完整性** | 2.9 定期审计、2.10 不删历史 | 3.6 敏感信息、5.5 债务登记、3.2 证据要求 | 决策/配置/回滚方式是否都有记录？ |
| **谱系性** | 12.3.2 进化登记（启用后 MUST） | 12.3.1 谱系块、12.3.3 G/L 分级、12.3.4 合并协议、12.4 经验库与跨项目吸收、12.5 简易版与升级路径、5.1 谱系巡检 | 本地改编是否带原因与通用性标签登记？副本相见时能否溯源？经验条目是否带问题签名与真实来源、可被其他项目识别与吸收？ |

**覆盖检查**：六项目标均有 ≥2 条规则/机制支撑（谱系性在规范被复制到第二个项目后才启用，启用前不检查）；若某行只剩一条，说明该目标依赖单点，应补强。

### 0.4 规范用语（RFC 2119 风格）

本文中的用语含义固定如下；**新写或修改条款时必须显式使用这些词**，不要混用「必须/建议/可以」与「最好/尽量/一般」。

| 用语 | 英文 | 含义 | 违反的后果 |
|---|---|---|---|
| **必须** | MUST | 强制项，违反即视为文档体系失效 | 审计判 **FAIL**，阻断发布 |
| **应当** | SHOULD | 默认执行；不执行必须说明理由并登记例外 | 审计判 **WARN** |
| **可以** | MAY | 可选，按项目需要启用 | 不检查 |

判断方法：问一句「如果违反它，文档体系是否还能自洽？」——不能＝**必须**；多数情况该做＝**应当**；看情况＝**可以**。

## 1. 文档分层：每份文档只回答一类问题

不要按「文件」组织文档，按「**回答什么问题**」分层。层与层的边界就是防矛盾的墙。

| 层 | 文档类型 | 只回答 | 典型文件 | 禁止 |
|---|---|---|---|---|
| **L0 入口层** | 项目入口 / Agent 手册 | 「怎么读、先读什么、红线是什么」 | `README.md`、`AGENTS.md`、`CLAUDE.md` | 不放具体数值与业务细节 |
| **L1 事实层** | 现状快照（**SSOT**） | 「**此刻是什么**」：版本、数量、路由、数据源口径、环境、部署状态 | `项目现状.md` | 不写「为什么」「计划」「历史」 |
| **L2 契约层** | 数据字典 / API 契约 / 设计规范 / 交互稿 | 「**怎么定义、为什么这样定义**」：字段、公式、阈值、枚举、页面行为 | `数据字典.md`、`API.md`、`UI规范.md` | 不写实时数值；不写进度 |
| **L3 过程层** | 变更日志 / 决策记录 / 运维手册 / 问题记录 | 「**发生了什么、怎么操作、怎么回滚**」 | `项目进度.md`、`ADR/`、`运维手册.md` | 不复制 L1 事实（引用即可） |

### 1.1 一条铁律

> **数值只住在 L1。其他文档引用 L1，绝不复制。**

复制一次 = 未来必然漂移一次。引用写法：
`见《项目现状》§2`，或 `当前版本以 /health 为准`。

### 1.2 文档地图

入口层必须维护一张「文档地图」：每份文档一行，写清**角色**与**什么时候该读它**。
超过 8 份文档仍没有地图，等于没有文档。

### 1.3 事实 ID 与引用

给事实源中的每个关键事实分配**稳定 ID**：`F-01`、`F-02`……

- ID **一经分配永不复用**；事实作废时保留 ID 并标注（如 `F-07（已作废，见 F-21）`）。
- 其他文档引用事实时写 **`F-07`**，**不写章节号**——章节会调整，ID 不会。
- 事实源模板必须含「ID」列（见 §8.2）；一个事实只对应一个 ID。
- 同一事实出现两个 ID、或 ID 指向的事实已不存在，均视为审计问题。
- 引用示例：`当前版本见 F-01（《项目现状》§1）`。

> 章节号是「位置」，ID 是「身份」。用 ID 引用，文档重组时不必全库改链接。

### 1.4 目录结构与命名

推荐结构（可按项目裁剪，但**同类文档必须放在同一处**）：

```
docs/
  项目文档体系规范.md      # 本规范
  项目现状.md              # L1 事实源
  项目进度.md              # L3 变更日志
  数据字典.md              # L2 契约（按需）
  API.md                   # L2 契约（按需）
  运维手册.md              # L3 过程
  adr/ADR-0001-<slug>.md   # 决策记录
  templates/               # 可复用模板
  archive/YYYY-<原名>.md    # 归档
```

命名与目录规则：
- **一个主题一份文档**；超过约 300 行考虑拆分，拆后必须有一份父文档做索引。
- 主文档名**不随日期变化**；日期前缀只用于归档（`YYYY-`）和 ADR 编号。
- 文件名风格全项目统一（中文描述名 **或** 英文 kebab-case），不要混用。
- 移动 / 重命名文档必须同步更新：文档地图、目录、所有引用，并跑死链检查。
- 归档保留原文件名与归档日期，放入 `archive/`；归档文档不再参与契约检查。

### 1.5 新增文档的准入与登记

> 新增文档是文档体系最常见的腐化入口：一事一文导致碎片化、同一事实出现第二份副本、孤儿文档无人引用。
> **新增前必须过「四问」，新增后必须完成「五步登记」。**

#### 第一步：四问——该不该新建

1. **主题是否已有文档？** 已有 → 扩展现有文档（或拆章节），不新建。
2. **读者与时态是否相同？** 同一读者、同为「现状 / 计划 / 历史」之一 → 并入现有文档。
3. **生命周期是否一致？** 一份长期维护、一份一次性 → 才拆开；一次性内容放 `notes/`，不进入正式体系。
4. **是否只是「另一种视图」？** 是 → 用生成脚本产出并标注「自动生成」，不手工新建（§2.1 例外）。

四问全部通过才允许新建；否则在变更日志里写明「为何不并入」。

#### 第二步：确定层级与位置

- 先定层：L0 入口 / L1 事实源 / L2 契约 / L3 过程（§1）。
- 再定位置与命名：按 §1.4 的目录结构与命名规则；**主文档名不带日期**。
- 若新文档将成为事实源或契约，必须在头部声明其**权威范围**（管什么、不管什么）。

#### 第三步：最小准入要件

新文档必须同时具备：

- [ ] 标题 + `最近更新：YYYY-MM-DD`
- [ ] 头部写明「**本文档回答 / 不回答**」（§3.3）
- [ ] 层级与权威范围明确；不是事实源/契约的，注明「以 X 为准」
- [ ] 不包含其他文档已有事实的**副本**（只引用，见 §2.1）
- [ ] 内部链接有效；引用它的旧文档已同步更新
- [ ] 含事实数值 → 已分配 `F-xx` 或明确引用事实源（§1.3）
- [ ] 若为决策 → 使用 `ADR-xxxx`（§6.1）；若为债务 → 使用 `D-xx`（§5.5）
- [ ] 无敏感信息（§3.6）

#### 第四步：五步登记

1. **文档地图**：新增一行（角色 + 什么时候读）。
2. **目录 / 索引**：顶层或长文档加入目录 / 索引。
3. **入口文件**：若属「必读」，更新必读顺序。
4. **变更日志**：记录「新增了哪份文档、解决什么问题」，并写「文档影响」。
5. **交叉引用**：在相关旧文档中加一句「详见 <新文档>」，避免孤儿文档。

#### 第五步：评审与生效

- 新文档随代码 / 变更**同一提交**评审（§4.3 清单）。
- 评审重点：层级是否错位、是否复制事实、是否与现有文档范围重叠。
- 生效后纳入 §5.4 新鲜度 SLO 与 §5.1 自动巡检范围。

#### 临时文档与草稿

- 会议纪要、草稿、调研笔记放 `notes/` 或 `drafts/`，**不进入文档地图**，不参与契约检查。
- 转正条件：被正式引用、需要长期维护、或有明确读者 → 按上述流程转为正式文档，并在变更日志留痕。
- 超过 30 天未转正的草稿：归档或删除（删除前确认无人引用）。

#### 反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 每个小主题新建一份文档 | 文档碎片化、找不到入口 | 先过四问，优先扩展现有文档 |
| 新文档复制事实数值 | 出现第二份 SSOT，必然漂移 | 只引用事实源 |
| 新文档不登记文档地图 | 孤儿文档，没人知道它存在 | 五步登记 |
| 新文档与旧文档范围重叠 | 两份都像「权威」，矛盾时无法裁决 | 先合并或明确分工与权威范围 |
| 草稿直接当正式文档 | 未评审内容进入体系 | 走草稿 → 转正流程 |

## 2. 十条核心规则（可直接照做）

> 等级定义见 §0.4。**「必须」项违反即审计 FAIL**；「应当」项不执行需登记例外。

| 规则 | 等级 | 适用条件 |
|---|---|---|
| 2.1 单一真相源 | **必须** | 总是 |
| 2.2 单一入口 | **必须** | 总是 |
| 2.3 变更留痕 | **必须** | 总是 |
| 2.4 只留日期 | **应当** | 总是 |
| 2.5 契约绑定 | **必须** | 存在被代码消费的定义时 |
| 2.6 发布三重记账 | **必须** | 存在发布 / 部署行为时 |
| 2.7 双份产物防御 | **必须** | 存在同源副本时 |
| 2.8 环境专属配置清单 | **必须** | 有部署环境时 |
| 2.9 定期审计 | **应当** | 总是（周期可按项目调整） |
| 2.10 不删历史 | **应当** | 总是 |

### 2.1 单一真相源（SSOT）

- 选**且只选一份**文档作为事实源（推荐 `项目现状.md`）。
- 所有「版本 / 测试数 / 指标数 / 路由数 / 锚点数 / 数据源 / 环境地址」类事实，**只在该文件维护**。
- 其他文档需要这些数字时：**引用，不复制**；引用时写明章节。
- 事实源本身要短：只放「此刻是什么」，目标 ≤ 100 行。历史与理由一律外移。

**生成型文档例外**：由脚本自动生成的视图（仪表盘、报告、导出表）**可以**包含事实数值，但必须：
① 在文件/页面显著位置标注「自动生成，勿手改」；② 注明生成脚本与数据来源；③ 修改只能改生成源，不手工维护。
未标注的生成物按普通副本处理（即违反 SSOT 规则）。

### 2.2 单一入口

- 项目根目录必须有**一个**入口文件（`README.md` 或 `AGENTS.md`/`CLAUDE.md`）。
- 入口文件包含：① 项目一句话定位 ② 必读顺序 ③ 文档地图 ④ 红线（合规/安全/不可改动项）⑤ 更新规则 ⑥ 引入烙印（家族成员必写，§12.3.7 固定两行，公开可查）。
- AI/新人开始工作时**先读入口**，再按顺序读；不允许「直接翻代码猜现状」。

### 2.3 变更留痕（倒序 + 同日合并 + 杂项）

变更日志是项目的「黑匣子」，格式固定：

```markdown
### YYYY-MM-DD · 一句话标题

> 起因 / 背景（谁在什么场景下提出）

**做了什么**：要点列表（含关键文件与行为变化）
**验证**：跑过什么命令、结果如何（测试数、构建、实测输出）
**发布三元组**（如涉及发布）：版本号 + commit + 部署时间

**同日杂项**：
- 不构成主线的零碎改动（依赖调整 / 仓库卫生 / 安全加固 / 文件归档 / 顺带修的小问题）
```

规则：
1. **新条目写在最上方**（倒序）。
2. **同一天的多次变更合并为一条**，不要一天十条。
3. **必须固定加「同日杂项」小节**——主线条目越长，边角事项越容易漏记。
4. 条目要能被**验证**：写命令、写结果、写 commit，而不是「已完成」。

### 2.4 只留「最近更新」日期，废除手工版本号

- 每份文档头部只写 `最近更新：YYYY-MM-DD`。
- **不要**给文档编号 `v1.3/v2.0`——它不携带信息、必然漂移、且需要全局同步。
- 规范 / 规则类文档的迭代用**日期制变更记录**（见 §13），同样不引入文档版本号。
- 代码发布版本（`CODE_VERSION`）是另一回事：它是**发布标识**，必须与前端/构建产物/健康检查一致（见 §2.6）。

### 2.5 契约文档与代码双向绑定

- 凡是「被代码消费的定义」——指标公式、阈值、枚举、字段名、路由、事件名——必须在契约层（L2）有且只有一份定义。
- 改代码必须同步契约；改契约必须同步代码。
- **能用脚本检查的，绝不用人眼盯**：版本一致性、路由清单、字段名、阈值常量、测试数，全部写成巡检脚本（§5.1）。
- 契约文档里写「**口径**」而不只是「值」：同名指标可能有两种口径（如两种美元指数），必须写明本项目的口径与出处。

### 2.6 发布三重记账（版本 + 提交 + 时间）

每次发布/部署，在变更日志中记录：

| 字段 | 来源 | 用途 |
|---|---|---|
| `CODE_VERSION`（或语义化版本） | 代码常量 | 回答「跑的是哪一版」 |
| `git_commit` + `git_dirty` | 健康检查 / 构建信息 | 回答「是不是可复现的这一版」 |
| 部署时间（含时区） | 部署记录 | 回答「什么时候上的」 |

并在服务上提供一个**可验证的端点**（如 `/health`）返回上述信息。
禁止只写「已部署」——三个月后没人知道部署的是哪个提交。

### 2.7 双份产物防御（契约漂移）

同一个东西若存在两份副本（旧前端/新前端、Web/小程序、多语言、文档/代码常量），必须：

1. 在**两份副本的源码注释里**互相点名：「本文件与 X 同源，必须同时修改」；
2. 审计时**两边都读**，不能只读有类型检查的一份；
3. 优先把常量收敛成**单一来源**（后端下发 / 构建注入），而不是人工同步两份。

> 经验：没有类型检查的那份副本最容易「安静地留着旧值」，且没有任何东西会报错。

### 2.8 环境专属配置清单

部署类项目必须维护一张表：**哪些配置会被部署覆盖、哪些不会、哪些必须手工回填**。

| 配置 | 位置 | 上传会覆盖？ | 处理 |
|---|---|---|---|
| 源码中的环境常量（如备案号） | 被跟踪源码 | ✅ 会丢 | 部署后立刻回填并提交 |
| `.env` | 服务器本地 | ❌ 不会 | 反向注意：不要把服务器 `.env` 拷回本机 |
| 构建产物 / 依赖目录 | 服务器自建 | ❌ 不会 | 代码有改动时重新构建 |
| 数据库 / 证书 / 备份 | 独立目录 | ❌ 不会 | 单独备份 |

凡是「**既被版本控制、又在服务器上被改过**」的文件，都是事故源。

### 2.9 定期审计节律

- 固定周期（建议 **每 2 周**，或每 N 次发布）做一次全量文档审计。
- 审计与整改**分开提交**：先出清单，再按级别修。
- 审计必须包含**数据/事实核查**，不能只看文字自洽。
- 审计结论**一律不可直接采信**，必须回读源码 / 实测环境（§5.2）。

### 2.10 永不删除历史

- 作废内容用 `~~删除线~~` 标记，并保留原文（可折叠/留档），不要直接删。
- 决策的理由比结论更重要：保留「为什么当时这样选」。
- 历史归档单独存放（`archive/` 或文档内「留档」小节），主文档保持精简。

## 3. 文档写作规范

### 3.1 事实、计划、历史必须区分时态

| 时态 | 标记 | 写法 |
|---|---|---|
| **现状** | 无标记 / ✅ | 「当前 405 例全绿」 |
| **计划** | ⏳ / P0–P3 | 「计划下周接入 X」 |
| **阻塞** | ⛔ | 「等用户提供密钥」 |
| **作废/历史** | ~~删除线~~ + 「原文留档」 | 保留但不参与现状判断 |

> 最常见的矛盾，就是**把计划写成现状**、或把历史数值当现状引用。

### 3.2 每条事实都必须可验证

- 数字带**口径 + 取数日期**：「约 1.47 万点（2026-10 取数）」。
- 动态增长的值**禁止写死**，标注「随采集增长，引用时注明取数日期」。
- 结论附**来源**：命令、日志、commit、文件:行号、接口响应。
- 「预期值」与「实测值」分开写；预期被实测推翻时，**保留预期并用醒目标记订正**。

### 3.3 每份文档的头部三件套

```markdown
# 文档标题
> 最近更新：YYYY-MM-DD
> **本文档回答**：……　｜　**不回答**：……
```

### 3.4 待办表只放未完成项

- 待办表保持精简；完成项**移入归档小节**（如 §5.1 存档），不要靠划掉完成项来「保留历史」。
- 待办按优先级（P0–P3）+ 依据（哪次讨论/哪次审计登记）排列。
- 阻塞项单独一张表：事项 / 状态 / 阻塞原因 / 需要的动作。

### 3.5 链接与命名

- 跨文档引用用**相对链接**（Obsidian 可用 `[[文件名]]`），定期跑死链检查。
- 文件名/术语全局统一：同一概念只用一个词；出现同义词时在术语表里指定「正式名」。
- 结论性文档（规范/字典）避免口语化；过程性文档（变更/问题）鼓励细节与现场输出。

### 3.6 敏感信息

- 文档中**禁止**出现真实密码、密钥、令牌、证书私钥、身份证号、手机号、银行卡号、完整内网拓扑等。
- 需要说明位置时用**占位符 + 指向管理位置**，如：`DB_PASSWORD=<见密钥管理；服务器 /root/.xxx，600 权限>`。
- 截图与日志示例先脱敏：账号打码、密钥截断、IP 可保留示例段。
- 审计时把「文档中出现疑似密钥/凭据」列为**高危项**。
- 提交前可用简单正则扫描：`password\s*=\s*\S+`、`BEGIN [A-Z ]*PRIVATE KEY`、`AKIA[0-9A-Z]{16}` 等。

## 4. 日常变更闭环（每次工作必走）

```
开始工作
  ↓
① 读入口 + 事实源 + 相关契约（不凭记忆）
  ↓
② 动手（代码/数据/设计）
  ↓
③ 工作结束前：写变更日志（倒序、同日合并、含验证与杂项）
  ↓
④ 同步事实源（版本/数量/路由/环境）
  ↓
⑤ 同步契约（公式/阈值/字段/交互）
  ↓
⑥ 更新受改文档的「最近更新」日期
  ↓
⑦ 提交（提交信息写清动机与影响面）
  ↓
⑧ 如发布：记「发布三元组」，回填环境专属配置
```

**漏掉任何一步，文档体系就开始腐化。** 其中 ③④⑤ 是最常被跳过的三步。

### 4.1 提交信息规范（推荐）

`类型(范围): 一句话动机`

- `feat` 新功能｜`fix` 修复｜`docs` 文档｜`refactor` 重构｜`chore` 杂项｜`test` 测试
- 正文写「为什么」，并列出受影响的契约/文档；发布提交必须含版本号与部署说明。

### 4.2 变更影响矩阵

> 改动**之前**先查这张表；表中没有的类型，先补表再改——否则一定会漏更新。

| 改动类型 | 必须同步的文档 | 触发时机 |
|---|---|---|
| 代码契约（字段 / 公式 / 阈值 / 枚举 / 路由） | 契约文档（字典 / API / 设计规范） | **同一提交** |
| 发布 / 部署 | 事实源 + 变更日志（发布三元组） | 发布当天 |
| 环境 / 配置（端口、域名、密钥位置） | 运维手册 + 环境专属配置清单 | 同一提交 |
| 数据源 / 口径变化 | 契约文档 + 事实源 | 同一提交 |
| 架构 / 不可逆决策 | ADR + 入口文件（若影响必读顺序） | 决策当天 |
| 文档新增 / 作废 / 重组 | 文档地图 + 目录 + 死链检查（新增须先过 §1.5 准入与五步登记） | 同一提交 |
| 依赖 / 工具链升级 | 运维手册 + 事实源（版本） | 同一提交 |
| 规范条款改编（增 / 改 / 裁 / 废，§12.3 已启用时） | 进化登记（§12.3.2，含原因与 G/L 标签）+ 头部谱系块（§12.3.1） | 同一提交 |
| 问题解决（达 §12.4.2 提取条件时） | 经验库（X 登记，含问题签名与来源）+ 变更日志（含参考/吸收记录） | 解决当天 |

### 4.3 文档评审清单（放进 PR 模板）

- [ ] 本次改动是否影响事实源中的数字 / 状态？→ 已更新（含事实 ID）
- [ ] 是否改动契约（字段 / 公式 / 阈值 / 枚举 / 路由）？→ 契约已同步
- [ ] 变更日志是否已写（含验证证据与「同日杂项」）？
- [ ] 受改文档的「最近更新」日期是否已更新？
- [ ] 是否新增文档？→ 已过 §1.5「四问」并完成「五步登记」
- [ ] 是否作废 / 重组文档？→ 文档地图与目录已更新
- [ ] 是否涉及敏感信息？→ 已脱敏
- [ ] 是否发布？→ 发布三元组已记录

## 5. 审计机制（发现矛盾与漏洞）

### 5.1 自动巡检（每次提交/每周）

写一个 `doc_audit` 类脚本，从**事实源**读取基准值，逐项比对。至少覆盖：

- [ ] 代码版本 ↔ 前端常量 ↔ 事实源表
- [ ] 测试数量 ↔ 事实源（实际执行 `--collect-only` 或解析测试文件）
- [ ] 关键数量（指标数 / 路由数 / 表数 / 锚点数）↔ 代码常量
- [ ] 文档头部的过期版本号 / 过期字符串
- [ ] 死链与失效 wiki 链接
- [ ] 契约字段 ↔ 代码中的字段名（能映射的尽量映射）
- [ ] 环境变量清单 ↔ 部署脚本实际使用
- [ ] 规范谱系块 / 进化登记 / 吸收溯源标记（§12.3 已启用时，明细见 §12.3.5）

输出格式统一：`[OK]/[WARN]/[FAIL] 检查项 + 实际值`，末尾给「N 通过 / N 警告 / N 失败」。

### 5.2 人工审计（双周）

1. **分范围并行**：入口层 / 工程与部署 / 契约↔代码 / 前端↔设计 / 过程层内部一致性，范围互不重叠。
2. **逐项回读源码或实测**——**审计结论不可直接采信**。经验：代理/模型给出的审计结论中有一部分会被实测推翻，必须逐项回读核实，不可照单全收。[源: 量化模型探索 E-02, 2026-10-29]
3. 问题分三类：**过期**（doc≠实际）、**矛盾**（doc↔doc）、**可疑**（无法证实）。
4. **归因到根因**：列出条目后，追问「为什么会同时出现这 N 处」——通常只有几类根因（多处副本、缺 SSOT、版本号手工维护、审计范围有盲区）。
5. 按严重度分级：**高**＝用户会看到错误信息/假数据；**中**＝可能出错；**低**＝洁癖级。
6. 报告末尾单列「**已核实不是问题**」——避免下次重复怀疑、重复排查。

### 5.3 已知盲区（必须专项检查）

- 待办表与阻塞表（最容易与变更日志脱节）
- 历史归档小节（「已完成」可能早就不是现状）
- 双份产物（旧前端/新前端、文档/代码常量）
- 部署手册 ↔ 部署脚本 ↔ 线上实际配置
- 文档里的「示例命令」与真实参数是否一致

### 5.4 新鲜度 SLO（建议值，按项目调整）

| 文档 | 更新期限 | 超期处理 |
|---|---|---|
| 事实源（SSOT） | 发布后 **1 个工作日**内 | 标 `> ⚠️ 待复核（自 YYYY-MM-DD 起）`，下次发布前必须更新 |
| 契约文档 | **与代码同一提交**（PR 内） | 评审阻断 / CI 阻断 |
| 变更日志 | 工作会话结束前 | 视为本次工作未完成 |
| 运维手册 | 每季度复核一次 | 把复核日期写入头部 |
| ADR | 决策当天 | — |

超期标记统一写法：`> ⚠️ 待复核（自 YYYY-MM-DD 起）`；巡检脚本可检查该标记与日期。

### 5.5 文档债务登记

维护一张「已知文档问题」表，避免问题只存在于记忆里：

| ID | 类型（缺失 / 过期 / 矛盾 / 待补） | 位置 | 影响 | 计划处理时间 | 状态 |
|---|---|---|---|---|---|
| D-01 | | | | | 未关闭 / 已关闭 |

- 债务项每次审计复核；超过**两个周期**未处理的，升级进待办表并标优先级。
- 关闭时保留记录（写明「已由哪次变更解决」），不要直接删行。

### 5.6 文档健康度量（建议指标）

| 指标 | 定义 | 参考目标 |
|---|---|---|
| 事实源陈旧天数 | 距最近一次更新 | 发布后 ≤ 1 天 |
| 死链数 | 相对链接 / wiki 链接失效数 | 0 |
| 契约一致率 | 自动巡检通过项 ÷ 总检查项 | 100% |
| 超期未复核文档数 | 超过 SLO 未更新的文档 | 0 |
| 文档债务存量 | 未关闭的债务项 | 持续下降 |

> 度量是**发现系统性问题的温度计**，不是考核 KPI；连续两个周期恶化就要查根因。

## 6. 文档生命周期

```
草案 → 生效 → 废弃（~~删除线~~ + 留档） → 归档（archive/）
```

- **生效**文档：参与 SSOT 与契约检查。
- **废弃**文档：保留原文与废弃原因，链接置灰，不删。
- **归档**：按主题/年份存放，主文档不再引用其内容，只保留入口链接。

### 6.1 决策记录（ADR）的触发条件

以下决策**必须**写 ADR（编号 `ADR-0001`，存放 `ADR/` 或 `docs/adr/`）：

- 不可逆或回滚成本高的决策（数据迁移、架构替换、对外接口兼容性）
- 跨模块 / 跨团队的决策
- 存在多个备选方案且有权衡的决策
- 与现有规范 / 契约冲突、但被批准为例外的决策

**不必写 ADR**：可逆的小改动、纯实现细节、已在变更日志中说明的一次性修复。

## 10. 反模式清单（真实踩坑总结）

| # | 反模式 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 同一数字复制到多份文档 | 同一事实最多曾出现在 7 份文档，过半审计问题源于此 | 数值只住 SSOT，其他处引用 |
| 2 | 文档手工维护 `vX.Y` | 必然漂移，且无人知道哪个是准的 | 只留日期；版本只用于代码发布 |
| 3 | 把「预期值」写成事实 | 预期 3521，实测 18194，差点按错的数清理数据 | 预期与实测分开写，实测后订正并留痕 |
| 4 | 把一次性命令当通用模板 | 判别式误伤正经历史数据 | 模板必须标注适用边界与前提 |
| 5 | 双份产物只改一边 | 无类型检查的那份安静保留旧值 | 同源物互相点名 + 审计两边都读 |
| 6 | 发布只记「已部署」 | 无法回答线上跑的是哪版 | 发布三元组 + 健康端点 |
| 7 | 文档只增不归档 | 真待办被历史淹没 | 完成项移入存档，待办表只放未完成 |
| 8 | 审计结论直接采信 | 多处结论被实测推翻 | 逐项回读源码/实测 |
| 9 | 把计划写成现状 | 读者按不存在的功能操作 | 现状/计划/历史三态标记 |
| 10 | 「跑完脚本＝生效」想当然 | 服务未重启，代码更新假生效 | 用可验证端点确认（版本/时间）而非脚本输出 |

## 11. 与 AI 协作的额外约定

> 本节不是可选建议：AI 参与项目时，以下条款与 §2 同等效力。

### 11.1 证据要求

- 任何结论必须给出来源：**文件 + 行号、命令 + 输出、接口响应、日志或 commit**。
- **「文档里写了」不算证据**——文档本身可能就是过期的；必须回读源码或实测。
- 预期值与实测值分开写；实测推翻预期时，保留预期并醒目标注订正。
- 无法验证时明确写「未验证」，不得用推测代替证据。

### 11.2 任务边界

- 大范围审计 / 调研必须**多路并行、范围互不重叠**；每路输出结构化清单（级别 / 位置 / 现状 / 应为 / 依据）。
- 明确要求 AI「不要修改范围外文件」；完成后列出实际改动清单。
- 子任务不得依赖其他子任务的中间结论；需要汇总时由主任务统一合并。

### 11.3 状态诚实

- **不得编造完成状态**：未运行就说未运行，失败就贴失败输出，部分完成就写部分完成。
- 「已修复」必须伴随验证证据；「已部署」必须伴随版本 / commit / 时间 / 健康检查结果。
- 不能因为「看起来对」就声称通过；不确定时标注不确定。
- 测试失败、构建失败、部署失败必须如实报告，不得省略或用「基本完成」掩盖。

### 11.4 会话与仓库的边界

- **长期有效的事实**写进仓库文档；**会话内的临时约定**留在对话里，二者不要混。
- 不把凭据、密钥、个人信息写进文档、提交信息或示例（见 §3.6）。
- AI 的文档改动同样走 §4 闭环，不允许只改文档不改事实源 / 契约。

### 11.5 提示模板（审计用）

```text
请审计 <范围>，要求：
1. 逐项回读源码 / 实测，不得采信文档中的数字；
2. 输出：级别（高/中/低）、位置（文件:行号）、现状、应为、依据；
3. 单列「已核实不是问题」；
4. 不要修改任何文件，只输出清单。
```

## 12. 可选扩展（按需启用）

> 以下机制在单人小项目中可暂缓；团队协作或文档数量增长后建议启用。

### 12.1 文档所有权（Owner）· 建议

给每份文档指定**唯一负责人**（RACI 简表）：

| 文档 | 负责人（Owner） | 审批人 | 备注 |
|---|---|---|---|

- Owner 是「最后负责人」，不一定是主要撰写者；负责确保文档随变更更新。
- **没有 Owner 的文档视为「无人维护」**，审计时应登记为文档债务。
- 小项目可以先在入口文件里写一句「所有文档由 <角色> 维护」，团队扩大后再拆分。
- 启用方式：在文档地图表里增加「Owner」一列即可，不必另建制度。

### 12.2 按项目规模裁剪 · 建议

| 规模 | 必须做 | 可以暂缓 |
|---|---|---|
| **单人小项目**（≤3 份文档） | TL;DR 5 条、§2.1–2.3、§4 | 独立契约文档、ADR、健康度量、PR 清单 |
| **小团队**（多人协作） | 全部 MUST 条款 + §4.3 PR 清单 + §5.2 审计 | 独立 ADR 目录、正式度量看板 |
| **多仓库 / 长期项目** | 全部条款 + §11 AI 协作 + §13 规范变更记录 | — |

> 裁剪只减少**文档数量**，不减少**单一真相源**与**变更留痕**这两条底线。

### 12.3 谱系登记与跨副本合并（Lineage & Merge）· 建议

> **启用条件**：规范被复制到第二个项目时。启用前本节不检查；启用后**登记是 MUST，合并协议是 SHOULD**。
> **一句话**：把规范的进化当 git 管理——谱系 ID 是仓库身份，进化登记是 commit log，fork 锚点是分支点，两个副本相见按协议合并；吸收的改进保留溯源标记（blame），谱系不断。
> 跨时空合并之所以可能，靠两条：① 登记时写**原因**（判断能否移植的货币）；② 追踪用 **ID 不用位置**（§1.3 同一哲学：章节会挪，身份不会）。
> **文档无关**：本节机制不绑定规范文档本身——规范副本是它的第一个应用。任何需要跨项目追踪进化、互换改进的文档（如 §12.4 经验库）原样适用本协议：各用各的谱系 ID 与登记表（E 登记泛化为 X 登记），合并、溯源、巡检规则不变。

#### 12.3.1 谱系块与 fork 锚点（副本随身携带）

每份规范副本的头部必须携带固定谱系块（与 §3.3 头部三件套同层）：

```markdown
> **谱系**：SPEC-DSS ｜ 角色：主线 | 副本
> **fork 自**：SPEC-DSS@<锚点：§13 日期 / tag / 源副本 E-ID>（本源写「—（本源）」）
> **归属**：<项目名 / 团队>
> **已合并**：— | <对方归属>@<吸收的 E-ID 列表，逗号分隔>
```

- **谱系 ID**（`SPEC-DSS`）在一切副本中恒定，规范重组、改名都不变——它回答「这份文档属于哪个规范家族」。
- **fork 锚点**＝这份副本分叉时，源版本的那条变更记录：从主线分叉 → 源规范 §13 日期制条目；从另一个副本分叉 → 源副本进化登记表（12.3.2）的对应条目（如 `projA-E-07`）。锚点是**身份不是位置**：源文档章节重排，锚点仍然有效。
- **tag 固化（规范在 git 仓库内时）**：规范每新增一条 §13 日期记录、或副本每新增构成新版本的 E 记录，给对应 commit 打 tag——主线 `dss-YYYY-MM-DD-<短hash>`，副本 `dss-<归属>-YYYY-MM-DD-<短hash>`；同日多条记录靠短 hash 保证唯一。fork 锚点可用 tag 代替日期：**tag 是机器身份，§13 日期是人类身份，二者指向同一版本、互相可验**（12.3.5 巡检项）。tag 由 git 在提交时管理，不构成 §2.4 所禁止的手工文档版本号。
- **角色**：任一时刻只有一份副本自认**主线**（负责汇集其他副本的反馈）；其余为**副本**。合并协议是对称的——任何两边都可以互吸——主线角色只决定「谁负责主动拉」。
- 谱系块缺失、谱系 ID 与正文不符 → 该副本视为**未登记**，不得参与合并；§5.1 巡检判 FAIL。

#### 12.3.2 本地进化登记（fork 的 commit log）

副本**不改写源的 §13**，而是自维护一张进化登记表（附在本小节末尾）：

| ID | 日期 | 类型 | 位置 | 变更摘要 | 原因与适用场景 | 通用性 | 状态 |
|---|---|---|---|---|---|---|---|
| E-01 | | 新增 / 修改 / 裁剪 / 作废 / 合并自 | §x 或条款名 | | **为什么改、在什么约束下改** | L / G | 生效 / 已取代（被 E-xx） |

- E-ID 每副本独立分配，**一经分配永不复用**（同 F-ID、ADR 编号的哲学）；合并后双方 E-ID 原样记录进对方登记，不重新编号。
- **登记即闭环**：对规范条款的任何增 / 改 / 裁 / 废，必须同时登记 E（走 §4 流程，见 §4.2 影响矩阵「规范条款改编」行）。**未登记的修改视为「未跟踪」**：合并时对方无义务保留；巡检发现先补登记，方可参与合并。
- 登记必须写**原因**，不能只写改动。原因是跨项目吸收的货币：12.3.3 的分级与 12.3.4 的合并判断都只看原因，不看改动本身。

#### 12.3.3 通用性分级（这条改进能不能带出去）

每个 E 项必须标注通用性：

| 标签 | 含义 | 合并时的行为 |
|---|---|---|
| **G 通用** | 原因不依赖本项目具体处境（如「预期值与实测值必须分开写」） | 对方**可直接吸收**；吸收条款保留溯源标记 |
| **L 局部** | 原因绑定本项目具体处境（如「我们部署有两个环境，补了环境表」） | **默认不入合并体**；对方认为有用时，在自己侧**重新登记**为新 E（L，注明「参考 <对方> E-xx」） |

- 分级在登记时完成；某条款的原因事后**普遍化**（在多个项目验证）时，升级为 G 并新登一条 E，**不修改旧行**（§2.10：不删不改历史）。
- 该标签防两种伤害：好规则因只在局部验证而被埋没（L 实为 G），以及局部调优被当普适规范导出（G 实为 L）。

#### 12.3.4 合并协议（两个副本相见时）

**触发**：两份同谱系 ID 的副本被放在一起比较（两个团队交换规范、主线汇集副本反馈）。步骤：

1. **识别**：互读谱系块，确认同谱系 ID、双方 fork 锚点与角色，**互查烙印编号**（同一编号被两个不同项目主张 → 按 12.3.7 冲突协议处理）；**定 LCA（最近共同祖先）**：双方各沿锚点回溯——主线侧按 §13 线性序，副本侧沿「合并自」链——取第一个共同版本。简化情形：双方都直接 fork 自主线时，LCA 即**较旧的那个锚点**（§13 主线线性，旧锚点必为新锚点的祖先）。
2. **枚举**：各列出 **LCA 之后**、对方登记中**没有**的 E 项（差集）；双方都已记录的不再进入。
3. **分类**：每个差集项归入四类之一：

   | 类别 | 判定 | 处理 |
   |---|---|---|
   | **重叠** | 双方独立做出同一实质改进（同位置、同效果） | 只留一份；双方各登一条 E 注「与 <对方> E-xx 独立收敛」——独立收敛本身就是规则正确的证据 |
   | **兼容** | 不同位置，或不冲突的增补（G） | **原样吸收**；条款保留溯源标记 `[源: <对方归属> E-xx, <日期>]`——这就是 blame 链 |
   | **冲突** | 同位置、不同实质 | **不自动裁决**，走 §6.1 ADR（背景＝双方版本，备选＝甲文本/乙文本），裁决标准按优先级：① 原因更通用者（G 胜 L）② 证据更强（§11.1：被更多项目验证 / 有真实事故记录）③ 影响面更小（保守优先）④ 仍平 → **冲突搁置**：主线保持现状，对方版本以 L 登记并注明理由，不强求统一答案；搁置即「延后」处置，进 §5.5 债务跟踪，下次合并强制复决 |
   | **局部** | 对方的 L 项 | 按 12.3.3：默认不入合并体 |

4. **回写**：合并后文件＝主体＋吸收项；**每个差集项的结局按四处置之一登记**——**采纳**（原样吸收，保留溯源标记）/ **改写**（己侧重登新 E，注明参考来源）/ **拒绝**（必须写明理由）/ **延后**（转入 §5.5 文档债务 D-xx，注明「下次合并强制复决」）；**合并事件本身登记 E**（类型＝合并自，列出吸收的 E-ID、来源与各差集项的处置）；双方谱系块「已合并」字段互记。
5. **锚点不动**：fork 锚点仍指原分叉点；谱系追踪靠 **E-ID 而非文件位置**——任何一边章节重排都不破坏合并。

> **例**：主线 fork 出副本 A（锚点 2026-10-28）。A 登记 E-01（G：新增「冲突搁置」裁决标准）、E-02（L：新增双环境配置表）。数月后两副本相见：E-01 属兼容 G → 主线原样吸收，条款标 `[源: A E-01, <合并日期>]`；E-02 属 L → 主线默认不吸收，若主线恰好也是双环境，则自行重登 E-03（L，参考 A E-02）。合并事件双方在登记中各记一条「合并自」。

> **节律**：建议并入 §5.2 双周审计（固定项「与已知副本比对进化登记」），或在副本交换时即时触发；审计与合并像审计与整改一样**分开提交**（§2.9）。

#### 12.3.5 谱系巡检（并入 §5.1）

自动巡检清单追加：

- [ ] 规范谱系块完整（谱系 ID / 角色 / fork 锚点 / 归属）
- [ ] 谱系 ID 与正文规范一致
- [ ] 本地规范条款修改有 E 登记，含原因与 G/L 标签
- [ ] 吸收条款带溯源标记；谱系块「已合并」引用的 E-ID 在登记中存在
- [ ] tag 已启用时：fork 锚点 ↔ tag ↔ commit 三者互验一致
- [ ] 引入烙印（§12.3.7）：入口文件含两行烙印（正式编号或预编号标记），与规范副本谱系块（版本 / 引入自）一致；**同一编号不被两个项目主张（冲突 → FAIL）**；有编号但主线名录查无 → WARN「待核对登记」；预编号标记 → WARN「待确认编号」（预期状态）

级别：谱系块缺失 → **FAIL**（未登记副本）；其余缺项 → **WARN**（先补登记）。

#### 12.3.6 运输与固化（git 实现）· 可选

> **分层声明**：谱系协议（12.3.1–12.3.5）记录在文档内、随文档传播，**不依赖任何 git 机制**；git 只回答「副本文件怎么在仓库之间移动」，是可选的运输层。无论选哪种运输，副本离开时都**必须**按 12.3.1 补谱系块。

按规模三选一：

| 方式 | 适用 | 做法 | 注意 |
|---|---|---|---|
| **直接复制** | 单人 / 小团队（默认） | 把规范文件拷入新项目，补谱系块声明为副本 | 零工具依赖；合并时人工走 12.3.4 |
| **模板仓 + PR** | 多团队共享同一规范源 | 规范主线住独立仓库，项目侧以 PR 回灌改进 | PR 即「合并事件」的自然载体，评审结论可入 ADR（§6.1） |
| **git subtree** | 多仓库长期协作：拉模板更新 / 回灌上游 | `git subtree pull --prefix=docs/template <模板仓> main`；回灌用 `git subtree push` 或 patch/PR | **`--squash` 会把子树历史压成一个提交**——子树历史不可再追溯，谱系身份改由 tag 承担；不带 `--squash` 则子树完整历史进入主仓（历史噪音大）。两种取舍都可用，但 subtree **只搬内容、不建谱系** |

> 仓库之间的同步机制可以换（复制 → subtree → 模板仓），副本侧的 **tag（12.3.1）与进化登记（12.3.2）才是谱系的真相**，不受运输方式影响。

#### 12.3.7 引入烙印与登记（Family Mark & Adoption Registry）

> **目的**：让每个引入本体系的项目带有一个**独特、公开可验证**的记号（烙印）——家族成员一眼相认，外部访问者/AI 读入口文件即知「这个项目属于哪个体系家族、引入的哪个版本」；主线同时维护一份公开成员名录（《引入登记.md》，编号 SSOT），它就是学习交流网络的入口。

- **烙印块（固定两行，入口文件头部）**：每个成员的入口文件（§2.2 第 ⑥ 项）在头部固定位置写入：

  ```markdown
  > 📜 **DSS-xxxx** ｜ 本项目已引入 [烙印系统](https://github.com/sir-yaoyue/Document-system)
  > 家族：SPEC-DSS ｜ 版本：本源 | 完整 | 简易 ｜ 引入自：<tag 或「—（本源）」>
  ```

- **预编号标记（编号确认前）**：项目尚未完成主线编号确认时，烙印行先写 `📜 DSS-⏳<项目名> ｜ 本项目已引入 [烙印系统](https://github.com/sir-yaoyue/Document-system)（待主线确认编号）`——**不含数字，结构上不可能撞号**；主线确认后替换为正式烙印两行。预编号是预期状态（巡检 WARN「待确认编号」），不是违规。
- **编号**：四位序号（`DSS-0001`…），**由主线统一分配**——本源所有者直接编辑《引入登记》；外部成员向主线仓库**提 PR 申请**（该 PR 即双方首次谱系接触，按 12.3.4 处理；主线核准编号后合并，成员再把编号写入自己入口文件）。**分配前必读《引入登记》最新发布状态**（git 仓库：先 fetch，**以 origin 快照为正典 SSOT**）；禁止基于过期快照分配。编号一经分配**永不复用**（§1.3 同哲学）；项目退役时编号保留、状态改「已退役」。
- **冲突协议（兜底）**：同一编号被两个不同项目主张（任何相遇或巡检发现）→ **FAIL（硬错误，必须上报主线）**；裁决优先级：① 已在主线**已发布**名录中登记者保号 ② 引入更早者保号 ③ 主线裁定（留痕）。改号方取下一空闲号，改号写入《引入登记》「更正映射」节（**留痕不删**，§2.10）；改号项目更新烙印行并在自己变更日志留痕。**改号不影响谱系**：fork 锚点、规范副本与 E/X 登记原样保留（编号是门牌，不是家谱）。
- **公开声明义务（MUST）**：烙印必须**公开可查**——写在仓库入口文件（任何访问者与 AI 按 §2.2 必读顺序第一眼可见的位置）；仅内部可见（私有笔记、会话约定）的声明不构成有效烙印。
- **一致性（三方互验）**：《引入登记》行 ↔ 成员入口文件烙印行 ↔ 成员规范副本谱系块（12.3.1）——**版本＝生效的规范文件、引入自＝fork 锚点 tag**，三者任一不一致即审计问题（12.3.5 巡检项）。SSOT 在《引入登记》，烙印行是其公开呈现，谱系块是其族内记录。
- **本源**：主线仓库自身持 `DSS-0001`（版本＝本源，引入自＝—（本源））。

### 12.4 经验总结与跨项目吸收（Experience & Absorption）· 建议

> **启用条件**：项目开始解决非平凡问题，或希望与其他规范使用者共享经验时。启用前本节不检查；启用后**经验库谱系登记是 MUST**（同 §12.3 等级），**经验提取是 SHOULD**（沉淀有裁量，漏提取不阻断，但审计时登记为债务）。
> **一句话**：把「问题是怎么解决的」提炼成**可识别、可复用、可转移**的条目，让本项目与其他项目在遇到同类问题时，都能把它作为**拓展思维的方向之一**。

#### 12.4.1 经验库与经验条目

- 每项目维护一本通用经验库 `经验总结.md`（L2：定义「这类问题怎么解」，被工作时的排查循环消费）。**领域专用经验可独立成库**（如 `UI设计经验.md`），通用库与领域库**只交叉引用、互不复制**（§1.4 一个主题一份文档；§2.1 防双份）。
- 经验库本身是**谱系文档**：头部带谱系块，用**自己的谱系 ID**（如 `EXP-DSS`），§12.3 机制原样适用——X 登记表即 E 登记的实例化（X-ID 永不复用、含原因、标 G/L、合并走 12.3.4 协议、巡检同 12.3.5）。
- 每条经验条目含**八字段**：

| 字段 | 要求 |
|---|---|
| **X-ID** | 每库独立分配，永不复用（§1.3 哲学） |
| **问题签名** | 让「第一次遇到它的人」能对上号的**现象描述**——条目的检索键；写不出签名 = 不可复用，不得入库 |
| **处境** | 问题发生的项目 / 技术 / 环境（一行即可） |
| **解决途径** | 有序步骤：有效路径 + 排除过什么（各一行）——途径是条目本体 |
| **原因** | 这条途径为什么有效——**可转移的部分**，吸收判断只看它（§12.3.2 同一原则） |
| **边界** | 什么情况下**不适用** |
| **通用性** | G / L（§12.3.3） |
| **来源** | 真实问题记录：项目 + 日期 + 变更日志 / 事故引用；**必填**——经验必须来自真实解决过的问题，禁止「待验证」入库（§11.1 证据要求；未验证的假设不配叫经验） |

#### 12.4.2 提取条件（什么时候问题变经验）

问题解决后问三问，**≥2 个「是」即提取**：

1. **可识别吗？** 存在一个别人（或未来的自己）遇到时能对上号的问题签名？
2. **可复用吗？** 途径依赖的是通用推理，而不只是本项目的运气 / 私有资源？
3. **会再遇到吗？** 这是一类问题，而不是一次性事件？

- 提取走 §4 闭环：当天登记经验库 + 变更日志（见 §4.2「问题解决」行）。
- **不必提取**：一次性问题；解法完全依赖项目私有信息；途径已被契约 / 手册覆盖（在变更日志里引用现有文档即可，不另立条目）。

#### 12.4.3 解题检索循环（遇到问题时）

```
遇到问题
  ↓
① 按问题签名检索本地经验库（通用库 + 相关领域库）
  ↓
② 命中 → 先核边界（我的处境在其适用范围内吗？）→ 按途径试
   未命中 → 正常解题
  ↓
③ 本地无解或想拓宽思路 → 查阅已知外部经验库条目（参考级吸收，12.4.4）
  ↓
④ 解决 → 过 12.4.2 三问，达标即提取入库
```

#### 12.4.4 外部经验的两级吸收

外部经验＝其他项目经验库中的条目（含主线经验库）。分两级：

| 级别 | 行为 | 成本 | 适用 |
|---|---|---|---|
| **参考（轻）** | 解题时引用「参考 <项目> X-xx」，记入变更日志；**不改本地库** | 零 | 借一个思路方向，但尚未在本地验证 |
| **纳入（重）** | 外部条目经本地验证适用（成功使用一次，或边界完全吻合）→ 按 §12.3.4 合并协议吸收进本地库（LCA / 四分类 / 四处置 / 溯源标记 `[源: <项目> X-xx, <日期>]`） | X 登记 + 谱系块更新 | 经验已在本地真实生效 |

- **思维方向条款**：外部经验是**拓展思维的方向之一，不是标准答案**——采纳前必须核边界；不适用时把「为什么这里不适用」写进变更日志，理由本身同样有价值，并可经合并协议**反向修正外部条目的边界**（双向学习）。
- 外部条目为 G 时纳入优先；L 时默认参考，仅当本地处境吻合才纳入（与 §12.3.4「局部」分类同构）。

#### 12.4.5 共享节律

- 「与已知副本 / 主线交换经验库」并入 §5.2 定期审计的固定项（节律同 §12.3.4：审计与合并**分开提交**，§2.9）。
- 共享是**双向**的：本项目 G 条目同样经谱系登记对外可吸收——**提取是为了被吸收，登记是为了能被吸收**。

### 12.5 简易版与升级路径（Simplified & Upgrade）· 建议

> **目的**：简单项目引入全套机制过重，但**体系间学习交流与进化共享**的必要内容不能丢。**简易版**（本仓库 `项目文档体系规范（简易版）.md`）是本完整版的**一份固定选条**：只保留参与交流闭环的条款，其余裁掉，被裁条款由升级触发器带回。
> **选条标准**：只保留服务于交流闭环的条款——**找到它**（入口/文档地图）→ **信任它**（SSOT/事实 ID/可验证/诚实）→ **记录它**（变更留痕/不删历史）→ **相见它**（谱系块/tag/合并协议）→ **吸收它**（G-L/经验库/两级吸收）。

#### 12.5.2 简易版的谱系身份

- 简易版**不另立谱系 ID**：属 SPEC-DSS 家族，角色＝**副本**，归属＝「简易版·分发标准」，fork 锚点＝创建时完整版最新 §13 条目（tag 优先）。
- 选条裁切登记为简易版的 **E-01（类型＝裁剪）**（§12.3.2），本表 12.5.1 是裁切清单的 SSOT。
- **同步义务**（§2.5 契约绑定的实例化：完整版＝源，简易版＝消费方）：完整版 §13 每出新条目，简易版必须检查选条是否受影响——受影响则同步正文并登记 E（类型＝修改，源＝完整版条目）；未受影响则只更新「选条最近检查」行。
- 简易版与完整主线相见时走 §12.3.4 协议：简易版侧（含简易项目）发现的 **G 级改进可回灌完整版**；完整版变更按选条同步。

#### 12.5.3 版本自检（给新使用者）

- **命中以下任一 → 用完整版**：① 文档数 >8 或即将超过 ② 存在被代码消费的定义（字段/公式/阈值/路由）③ 存在发布 / 部署行为 ④ 多人 / 多角色协作 ⑤ 需要定期审计节律或健康度量。
- 都没命中 → 用简易版。**拿不准选完整**——完整版≈超集，升级零迁移成本，降级要判断。
- **重检时机**：自检不是只做一次——**每次副本交换时、或发现任一触发器疑似命中时，重跑本自检**；简易版项目把重检写进 `项目进度.md` 待办首行（每次工作前看一眼）。触发器大多单调（项目很少失去代码契约或发布行为），命中后基本不会撤销（见 12.5.4 升级路径）。

#### 12.5.4 升级 / 降级操作

- **升级（简易 → 完整）**：文件替换为完整版 → 谱系块 fork 锚点改指完整版最新 §13 条目 → 本副本的 E/X 登记**原样继承**（登记跟随项目，不随版本文件重置）→ 登记一条 E（类型＝修改，「简易→完整升级」）→ 此后按完整版执行。
- **降级（完整 → 简易）**：允许；登记永不删除（§2.10）——文件替换、继承登记、登记一条 E（类型＝裁剪，「降级」，列明不再强制的条款）。
- **继承原则**：进化登记（E）与经验库（X）跟随**项目（副本）**，不跟随版本文件——换版本不是换谱系。
